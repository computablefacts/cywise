<example>
Voici un exemple du format attendu pour une vulnérabilité "Exposed .git Directory":

### Solution simplifiée
- Bloquer l'accès au répertoire .git via la configuration du serveur web
- Vérifier qu'aucun fichier sensible n'est accessible publiquement
- Redémarrer le service web pour appliquer les changements
- Tester l'accès depuis l'extérieur pour confirmer le blocage

### Solution détaillée

**Étape 1: Modifier la configuration Nginx**

Éditer le fichier de configuration du vhost (généralement dans /etc/nginx/sites-available/):

```nginx
# AVANT (vulnerable)
location / {{
    try_files $uri $uri/ =404;
}}

# APRÈS (sécurisé)
location / {{
    try_files $uri $uri/ =404;
}}

location ~ /\.git {{
    deny all;
    return 404;
}}
```

**Étape 2: Tester la configuration**
```bash
sudo nginx -t
```

**Étape 3: Appliquer les changements**
```bash
sudo systemctl reload nginx
```

**Impact:** Aucun downtime, rechargement à chaud de Nginx.

**Bonne pratique:** Ne jamais déployer le dossier .git en production. Utiliser un processus de build/deploy qui exclut les fichiers de versioning.

### Risques (si non corrigé)
Un attaquant peut télécharger l'intégralité du code source de l'application via le répertoire .git exposé, révélant potentiellement des secrets (clés API, mots de passe) et la logique métier complète de l'application.

### Vérification
1. Tester l'accès: `curl -I http://{ip}:{port}/.git/config` (doit retourner 404)
   - Explique: Cette commande teste si le fichier est accessible. Un code 404 signifie que l'accès est bien bloqué.
2. Vérifier les logs Nginx: `tail -f /var/log/nginx/access.log` (accès bloqués)
   - Explique: Vérifie que les tentatives d'accès sont bien refusées dans les logs du serveur.
3. Scanner avec outil: `./gitdumper.sh http://{ip}:{port}/.git/` (doit échouer)
4. **OBLIGATOIRE: Relancer un scan Cywise** pour confirmer que la vulnérabilité n'apparaît plus dans les résultats
</example>
